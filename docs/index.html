Fault-Tolerant Distributed Key-Value Store

A CP key-value store implementing the Raft consensus algorithm in Go — deployed on Google Cloud Platform and verified under OS-level fault injection. Think of it as a small etcd: the same class of system that backs Kubernetes' control plane, built from the consensus layer up.

Overview

Distributed storage forces a choice when the network splits. This system chooses consistency over availability: under a partition, the minority side stops serving rather than return data it can no longer prove is current.

That choice is enforced mechanically, not by convention. Every read on the leader is preceded by a VerifyLeader() heartbeat round-trip to a majority. A leader that has silently lost contact with the cluster — and does not yet know it — fails that check and refuses to serve.

Why this matters. The dangerous failure in distributed storage is not a crash; a crashed node obviously serves nothing. It is a node that is confidently wrong — a deposed leader still answering reads with stale data because no one has told it that an election happened. Preventing that is what most of the machinery below exists for.

System Architecture

Each VM runs exactly two processes on separate ports. The separation is deliberate: consensus traffic and client traffic must be independently disruptable, or fault injection cannot isolate which layer a failure affects.

Theoretical minimum MTTR = heartbeat + election = 1250 ms. Observed MTTR matched it almost exactly, because detection is deterministic: the election timer fires a fixed interval after the last heartbeat, and in a quiet cluster the first follower to time out wins immediately.

Consensus Mechanics

Raft replicates a log. Every state change becomes an ordered entry, and a node may apply an entry to its state machine only once a majority has durably stored it. Agreement on log order yields agreement on state.

Leader election

sequenceDiagram
    autonumber
    participant F1 as Follower A
    participant L as Leader (dying)
    participant F2 as Follower B

    L->>F1: AppendEntries (heartbeat)
    L->>F2: AppendEntries (heartbeat)
    Note over L: crash / partition
    Note over F1,F2: silence...
    Note over F1: 500 ms heartbeat timeout
    Note over F1: +750 ms election timeout fires
    F1->>F1: term++, vote for self
    F1->>F2: RequestVote (term N+1)
    F2-->>F1: vote granted
    Note over F1: 2 of 3 = majority
    F1->>F2: AppendEntries (new leader)
    Note over F1,F2: ~1.25 s total
A candidate needs ⌊N/2⌋+1 votes — 2 of 3, or 3 of 5. Requiring a strict majority is what makes two simultaneous leaders impossible.

Why a majority, specifically? Any two majorities of the same cluster must share at least one member. That overlapping node cannot vote for two different leaders in the same term — so split-brain is excluded arithmetically rather than by timing luck.

Read & Write Paths

Write path

sequenceDiagram
    autonumber
    participant C as kv-client
    participant F as Follower
    participant L as Leader
    participant P as Peers
    participant M as FSM + BoltDB

    C->>F: Set(foo=bar)
    F-->>C: redirect → leader address
    C->>L: Set(foo=bar, clientID, seqNum)
    L->>L: append {SET, foo, bar, clientID, seqNum}
    L->>P: AppendEntries
    P-->>L: ACK
    Note over L: quorum reached
    L->>M: FSM.Apply()
    M->>M: dedup check (clientID, seqNum)
    M->>M: write to BoltDB
    M->>M: lastSeq[clientID] = seqNum
    L-->>C: success
The response is returned only after the entry is durable and committed by a majority. Acknowledged writes survive a leader crash.

Exactly-once writes. A client that retries after a leader change would otherwise apply the same operation twice. The FSM keeps a per-client (client_id → last_seq) table, so a duplicate is recognised and skipped. Because the table lives inside the state machine, it is replicated and snapshotted with the data — surviving leader changes and node restarts alike.

Read paths

Two mechanisms, both linearizable, trading latency against leader load.

    rect rgba(42,111,151,.10)
    Note over C,P: Leader read — VerifyLeader
    C->>L: Get(foo)
    L->>P: heartbeat to majority
    P-->>L: ACK
    L-->>C: value
    end

    rect rgba(184,121,31,.10)
    Note over C,P: Follower read — Read-Index (v1.3)
    C->>F: Get(foo, follower_read=true)
    F->>L: GetReadIndex()
    L->>P: confirm leadership
    L-->>F: commit_index = N
    F->>F: block until appliedIndex ≥ N
    F-->>C: value (served locally)
    end
Read-Index lets followers serve linearizable reads: they learn how current they must be, wait to reach that point, then answer from local state.

VerifyLeader() costs one round-trip (~30 ms cross-zone on GCP) on every read. That is the price of never serving stale data from a deposed leader.

Failure Handling

What the implementation actually does — not textbook Raft, but the behaviour observed under test.

stateDiagram-v2
    [*] --> Healthy
    Healthy --> LeaderLost: leader killed / partitioned
    LeaderLost --> Electing: heartbeat + election timeout
    Electing --> Healthy: majority elects new leader (~1.25 s)
    Electing --> Unavailable: no majority reachable

    Healthy --> Partitioned: network split
    Partitioned --> MinorityBlocked: minority side
    Partitioned --> Healthy: majority side continues
    MinorityBlocked --> Healthy: partition heals, log catch-up

    Healthy --> NodeDown: process crash
    NodeDown --> CatchUp: restart
    CatchUp --> Healthy: AppendEntries or InstallSnapshot
    Unavailable --> Healthy: quorum restored
The minority side of a partition blocks rather than diverging — this is the CP guarantee made concrete.

Chaos-Testing Infrastructure

Faults are injected by a sidecar that operates below the application — using OS primitives the system under test cannot intercept or route around.

FaultMechanism
Process killkill -9 <pid>
Freeze / thawkill -STOP / -CONT — simulates a GC pause or a hung process
Network partitionBidirectional iptables -A INPUT/OUTPUT … -j DROP
Latency injectiontc qdisc add dev <nic> root netem delay Xms, applied to the full NIC
NIC discoveryip route get 8.8.8.8 — GCP Debian uses ens4, not eth0

Two bugs where the tests were silently passing for the wrong reason. Both were found by checking whether the fault injector was doing what it claimed — not by a failing test.

BUG-4 — unidirectional partition. The first implementation dropped only INPUT. The "isolated" node could still send heartbeats outward, so peers never considered it gone. Every partition test had been validating a partition that did not exist. Fixed by dropping INPUT and OUTPUT.

BUG-5 — netem on the wrong scope. Latency was applied to eth0 (absent on GCP) and scoped to the Raft port only — so heartbeats on other ports still arrived on time and no election was triggered. Fixed by auto-detecting the NIC and delaying all traffic on it.

A passing chaos test proves nothing until you have verified the chaos.

The quorum bypass

The clearest empirical result: where latency lands matters far more than how much there is.

ConditionLatencyThroughputvs baseline
Baseline15.9 ms/op62.9 ops/s—
Slow follower (+2000 ms)16.3 ms/op61.3 ops/s−2.5%
Slow leader (+500 ms)1645 ms/op0.6 ops/s−99%

A follower delayed by two full seconds costs 2.5% throughput. The leader delayed by a quarter of that destroys 99% of it.

Why. In a 3-node cluster the leader commits once it has its own write plus any one follower — so the slowest node is simply never on the critical path. Quorum means a lagging minority cannot serialize the majority. The leader, by contrast, is on every write path by definition; delaying it delays everything, and at 500 ms its own heartbeats miss their deadline and trigger an election.

Limitations

Stated plainly, because they bound what the numbers above mean.

LimitationDetail
No linearizability checkerCorrectness is validated by hand-designed scenarios, not by recording operation histories and checking them mechanically (Jepsen/Porcupine). This is the clearest gap and the highest-value addition.
No pre-voteA partitioned node that rejoins with an inflated term can disrupt a stable leader. A known Raft extension, not implemented here.
Aggressive election timeout1.5× heartbeat, below HashiCorp's recommended 5–10×. Empirically stable in these conditions, with one observed spurious election under heavy load. Tuned for a ~15 ms cross-zone RTT — not validated at scale or under adversarial load.
Modest absolute throughput~63 ops/s on e2-micro instances, with no batching or pipelining of AppendEntries. The interesting result is the relative behaviour, not the raw number.
No metrics endpointCluster state is observable via logs and the dashboard, but there is no Prometheus surface for term, commit index, or replication lag.
Empirically verified, not formallyNo TLA+ specification or proof. Confidence rests on the test suite and the design, not on formal methods.
Byzantine faults out of scopeRaft assumes crash-stop, not malicious, participants.

If continued, in order: (1) record operation histories and run them through Porcupine for mechanical linearizability checking; (2) add pre-vote; (3) expose Prometheus metrics; (4) batch and pipeline AppendEntries for throughput.
