### BUG-1: Script crashes if a VM is not SSH-ready within 15 seconds (HIGH)

**What happened:**
The first `dynamic_deploy.sh` run failed with:
```
ssh: connect to host 136.115.46.81 port 22: Connection refused
ERROR: (gcloud.compute.ssh) [/usr/bin/ssh] exited with return code [255]
```
Node2 was created successfully but its `sshd` daemon hadn't started yet when the cleanup
step ran. `set -euo pipefail` (line 4) treated this as a fatal error and aborted, leaving a
half-bootstrapped cluster.

**Root cause:**
Step 4 waits only `sleep 15` after creating VMs before making SSH calls. e2-micro instances
in `us-central1-c` have occasionally needed 30–50s for `sshd` to be reachable in practice.

**Fix needed:**
Replace the flat `sleep 15` with a proper SSH-readiness poll, matching the pattern already
used for agent health checks in steps 7/8. For each VM, retry the SSH call in a loop until
it succeeds or a deadline is reached:
```bash
wait_ssh() {
  local node=$1 zone=$2
  local deadline=$((SECONDS + 90))
  until gcloud compute ssh "$node" --zone="$zone" --quiet -- "true" 2>/dev/null; do
    [ $SECONDS -ge $deadline ] && { echo "❌ $node SSH not ready after 90s"; exit 1; }
    echo "    ...waiting for $node SSH (${SECONDS}s)"; sleep 5
  done
}
# Call before any SSH step:
for i in $(seq 0 $((NODE_COUNT - 1))); do wait_ssh "${NODES[$i]}" "${ZONES[$i]}"; done
```

### BUG-2: `chmod +x ~/*.sh` prints error on nodes without .sh files (LOW)

**What happened:**
```
chmod: missing operand after '+x'
```
Printed on node1 and node2 during the permissions step. The relevant line:
```bash
"chmod +x ~/node-agent ~/kv-store ~/kv-dashboard ~/kv-chaos ~/kv-client; \
 shopt -s nullglob; chmod +x ~/*.sh; true"
```
`shopt -s nullglob` makes unmatched globs expand to the empty string. On node1/node2 (which
have no `.sh` files), `~/*.sh` expands to nothing, so `chmod +x` is called with zero
arguments → error. The `; true` suppresses the exit code but not the stderr output,
which confuses log readers.

**Fix needed:**
Use `find` or a conditional:
```bash
"chmod +x ~/node-agent ~/kv-store ~/kv-dashboard ~/kv-chaos ~/kv-client; \
 find ~/ -maxdepth 1 -name '*.sh' -exec chmod +x {} +"
```
Or simply only chmod `.sh` on node0 (the only node that receives them):
Move the `.sh` chmod into the `if [ "$i" -eq 0 ]` block.

### WARN-1: macOS tar extended attribute warnings on Linux VMs

**What happened:**
```
tar: Ignoring unknown extended header keyword 'LIBARCHIVE.xattr.com.apple.provenance'
```
(Repeated 5× per VM, once per binary in the tarball.)

macOS's `tar` embeds Apple-proprietary extended attributes (`com.apple.provenance`,
`com.apple.quarantine`, etc.) into tarballs. Linux ignores them but prints a warning
per entry. No functional impact.

**Fix needed:**
Set `COPYFILE_DISABLE=1` before the tar call to suppress macOS metadata injection:
```bash
COPYFILE_DISABLE=1 tar -czf "$BIN_DIR/binaries.tar.gz" -C "$BIN_DIR" \
  kv-store kv-client kv-chaos kv-dashboard node-agent
```
Or use GNU tar if installed (`gtar` via Homebrew).

### WARN-2: "Pseudo-terminal will not be allocated" printed on every SSH call

Every `gcloud compute ssh ... -- "command"` call without an interactive TTY prints:
```
Pseudo-terminal will not be allocated because stdin is not a terminal.
```
With 3 nodes × ~8 SSH steps = ~24 occurrences per deploy run. Not a failure,
but makes output very hard to read.

**Fix needed:**
Add `--ssh-flag="-T"` (or `-q` inside the remote command) to non-interactive SSH calls:
```bash
gcloud compute ssh "$NODE" --zone="$ZONE" --ssh-flag="-T" --quiet -- "command"
```

### FEAT-1: No leader election verification after deploy

The deploy ends after confirming all `node-agent` health endpoints return `"alive":true`.
But this only means the *agent* (wrapper) is up — the inner `kv-store` Raft process could
still be bootstrapping, waiting for quorum, or stuck in an election loop.

A deploy that looks successful to the script may have an unelected cluster. The demo
starts from this assumption and would break immediately.

**Fix needed:**
Add a final verification step that polls the dashboard `/api/cluster` endpoint until
a leader appears (with a 30s timeout):
```bash
echo "🗳  Waiting for Raft leader election..."
DEADLINE=$((SECONDS + 30))
until curl -sf "http://${EXT_IPS[0]}:${DASHBOARD_PORT}/api/cluster" 2>/dev/null \
      | python3 -c "import sys,json; d=json.load(sys.stdin); \
        leaders=[n for n in d['nodes'] if n.get('state')=='Leader']; \
        exit(0 if leaders else 1)"; do
  [ $SECONDS -ge $DEADLINE ] && { echo "❌ No leader elected after 30s"; exit 1; }
  echo "    ...waiting for leader (${SECONDS}s elapsed)"; sleep 3
done
echo "✅ Raft leader elected — cluster fully operational."
```

### FEAT-3: No end-to-end smoke test at the end of deploy

After the cluster is up, the deploy script never sends a real KV operation to verify
the full write path is working (client → gRPC → Raft consensus → FSM → response).
A deployer has no programmatic confirmation that the cluster is actually serving requests.

**Fix needed:**
Add a quick smoke test at the very end using the already-compiled `kv-client`:
```bash
echo "🧪 Smoke test: writing + reading a key..."

  -cmd set -key deploy_probe -val ok

  -cmd get -key deploy_probe | grep -q "ok" && echo "✅ Smoke test passed" \
  || echo "❌ Smoke test FAILED"
```

### BUG-4: `/api/partition` only blocks INCOMING Raft traffic — insufficient to isolate a leader (HIGH)

**Observed:**
N6 (iptables leader partition) produced 3 cascading failures:
- N6a FAIL: "Same leader still elected" — no new election fired
- N6c FAIL: "Isolated leader ACCEPTED write" — flagged as safety violation
- N6e FAIL: "Former leader state is 'Leader' after heal"

**Root cause:**
The node-agent's partition implementation applies:
```
iptables -A INPUT -p tcp --dport <raft-port> -j DROP
```
This blocks packets *arriving at* the target node's Raft port. But the leader's *outgoing*
heartbeats to followers are unaffected. Followers still receive heartbeats → election
timeout never fires → the "partitioned" leader stays leader and can freely commit writes
(it can still reach both followers outbound).

N1 (follower partition) worked correctly for a different reason: blocking a follower's
incoming Raft traffic stops it from receiving AppendEntries, which is the observable
effect being tested (follower falls behind). The leader's quorum path is unaffected.

**Fix needed:**
The agent partition should block *both directions*:
```bash
# Block incoming to this node's Raft port (stops receiving AppendEntries ACKs)
iptables -A INPUT -p tcp --dport <raft-port> -j DROP
# Block outgoing from this node to peer Raft ports (stops heartbeats reaching followers)
iptables -A OUTPUT -p tcp --dport <peer0-raft-port> -j DROP
iptables -A OUTPUT -p tcp --dport <peer1-raft-port> -j DROP
```
The agent already knows the peer ports from its config. This is a change to `cmd/agent/main.go`.

### BUG-5: netem only delays Raft-port traffic, not gRPC client traffic (MEDIUM)

**Observed:**
N2, N3 (netem on follower/leader) and Phase 3 R2 all showed minimal client-observable
latency increase despite 500ms netem configured:
- N3: 105ms baseline → 119ms with 500ms leader delay (+14ms, not +500ms)
- R2: 186ms baseline → 210ms with 500ms leader delay (+24ms)

**Root cause:**
The netem tc rule is scoped to the Raft port (e.g., port 12002), not the entire network
interface. `kv-client` sends writes to gRPC port 50052 — a different port, not subject
to the tc filter. The delay only applies to Raft consensus traffic (AppendEntries,
RequestVote), so only the inter-node replication path is slowed, not the
client-to-leader RPC path.

This means:
1. The test intent for R2 ("does slow leader raise client latency?") is not actually
   being measured — it's measuring Raft replication latency instead.
2. The N2/N3 latency numbers are misleadingly small in test output.

**Fix needed:**
Apply netem to all traffic on the interface, or explicitly include the gRPC port range:
```bash
# Option A: apply to all traffic on eth0 (simpler, more realistic)
tc qdisc add dev eth0 root netem delay ${delay}ms

# Option B: apply to both Raft and gRPC ports via u32 filters
# Add filter for port 50051-50053 in addition to 12000-12002
```
Change in `cmd/agent/main.go` netem handler.
