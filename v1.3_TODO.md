## 🐛 New Bugs (Discovered in 2026-04-01 Code Evaluation)

### BUG-NEW-1: `seqNum=0` silently ignored in `kv-client` (LOW)

**File:** `cmd/client/main.go`

**What happens:**
The client flag `-seq-num=0` is parsed but treated as "not set" (zero-value ambiguity in Go).
A user explicitly passing `-seq-num=0` to test idempotency at sequence number zero gets
auto-incremented seqNum instead — the test silently measures the wrong thing.

**Fix needed:**
Use a sentinel (e.g., `-1` or a separate `-use-seq-num` bool flag) to distinguish
"user wants seqNum=0" from "user didn't set seqNum."

---

### BUG-NEW-2: `AddVoter` / `RemoveServer` calls have no deadline in `node.go` (MEDIUM)

**File:** `server/node.go` (Join handler, ~lines 281–334)

**What happens:**
`raft.AddVoter()` and `raft.RemoveServer()` are called without a timeout future.
If the cluster is in a degraded state (election in progress, slow leader), the join
goroutine blocks indefinitely. Under the `set -euo pipefail` deploy script, a stalled
join would eventually hang the entire deploy.

**Fix needed:**
Wrap with a deadline future and check the error:
```go
f := r.raft.AddVoter(raft.ServerID(id), raft.ServerAddress(raftAddr), 0, 10*time.Second)
if err := f.Error(); err != nil {
    return fmt.Errorf("AddVoter failed: %w", err)
}
```

---

### BUG-NEW-3: Heartbeat/election timeout ratio is 1.5× — below recommended minimum (LOW)

**File:** `server/node.go` (Raft config, ~lines 51–62)

**What happens:**
`HeartbeatTimeout=500ms`, `ElectionTimeout=750ms` → ratio = 1.5×.
The HashiCorp Raft library recommends ≥ 2× to tolerate one missed heartbeat before
triggering a candidate election. On GCP e2-micro (noisy-neighbor scheduling), a single
delayed heartbeat at the 1.5× ratio can trigger a spurious election during a busy write burst.

**Fix needed (two options):**
- Option A: Raise ElectionTimeout to 1000ms (keeps 500ms MTTR detection, safer ratio = 2×)
- Option B: Add a comment in code documenting why 1.5× is intentional and acceptable
  (e.g., "empirically validated on GCP e2-micro cross-zone RTT ~15ms; spurious elections
  observed to be rare and self-healing within one term")

## 🟡 Medium Items (Carried from v1.2)

### M-3: Heartbeat/election timeout ratio not documented (Doc)

**File:** `system_design_v12.md`

Add a "Timing Rationale" paragraph justifying the 500ms/750ms choice:
- GCP cross-zone RTT baseline: ~15ms
- e2-micro noisy-neighbor jitter: up to ~50ms bursts
- 500ms gives 10× headroom above worst-case RTT
- 750ms election timeout means one missed heartbeat doesn't trigger spurious election
  (at 1.5× ratio; see BUG-NEW-3 for the trade-off)

## 🔴 Hard Items (Carried from v1.2)

### H-1: Peer Raft port list is static (baked in at deploy time)

**Files:** `cmd/agent/main.go`, `dynamic_deploy.sh`

The `-peer-raft-addrs=ip:port,...` flag is passed at deploy time and stored in the agent.
This means the agent cannot adapt if cluster topology changes (e.g., a node is replaced).

**Fix needed:** Agent reads peer Raft ports from `/api/cluster` endpoint at partition time,
eliminating the static `-peer-raft-addrs` flag. Requires a `/api/cluster` call inside the
`/partition` handler before building iptables rules.
